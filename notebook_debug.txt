=====================================================
SECTION: Encoder noise / wheel_encoder counting
=====================================================

-----------------------------------------------------
[2026-08-06] Issue: wheel_encoder count drifting/decreasing on its own
-----------------------------------------------------

SYMPTOM
- Left-side encoder count would decrease continuously by itself.
- First suspected: only happening right at motor start.
- Confirmed by testing: it continues even while the robot is
  completely idle (motors off, no cmd_vel commanding motion).

ROOT CAUSE
- The encoder ISR (leftEncoderISR / rightEncoderISR in src/main.cpp)
  only validated two things per pulse:
    1. Width  — pulse must stay HIGH long enough (LEFT/RIGHT_MIN_PULSE_WIDTH_US)
    2. Gap    — must be spaced out from the last accepted pulse
                (LEFT/RIGHT_ENCODER_DEBOUNCE_US)
- Neither check knows whether the wheel is actually supposed to be
  turning. Electrical noise (EMI, motor switching transients, etc.)
  that happens to pass both checks gets counted as a real pulse,
  and if it's biased in one direction, it looks like a steady drift
  rather than random jitter.

FIX APPLIED
- Added a "stationary gate" to both ISRs: a pulse is only counted if
  the robot is currently commanded to move (motorsWereStopped == false,
  set from cmd_vel in set_motors()). If nothing should be turning the
  wheel, any pulse that arrives is treated as noise — bumped into the
  glitch counter instead of the pulse counter, no direction is even read.
- Location: leftEncoderISR() / rightEncoderISR() in src/main.cpp,
  right after the width+gap checks, before the direction read.

TRADE-OFF TO REMEMBER
- Manually spinning a wheel by hand (no cmd_vel sent) will NOT be
  counted anymore. This is intentional — expected side effect of the
  fix, not a bug.

-----------------------------------------------------
[2026-08-06] Regression: encoder stopped counting during real driving
-----------------------------------------------------

SYMPTOM
- After the stationary-gate fix above, encoder count stayed flat
  (stable) even while actively driving with teleop — not just at rest.

ROOT CAUSE
- The stationary gate is driven by commandingMotion in set_motors():
    bool commandingMotion = (fabs(left) > DEADBAND) || (fabs(right) > DEADBAND);
- DEADBAND was 0.02 (2% of full [-1,1] command scale). This was meant
  only to filter floating-point noise around exact zero, but it ended
  up rejecting real teleop commands whose per-wheel magnitude was
  smaller than 0.02 — so motorsWereStopped never flipped to "moving"
  even though PWM was clearly nonzero and the wheel was visibly
  spinning (motor drive itself has no deadband).

FIX APPLIED
- Lowered the deadband from 0.02 to 0.005 (named MOTION_DEADBAND in
  set_motors(), src/main.cpp). Still swallows float/controller noise
  at exact zero, but no longer blocks legitimate slow-speed commands.

-----------------------------------------------------
[2026-08-06] Two-encoder hardware mismatch — decision to run on one encoder
-----------------------------------------------------

CONTEXT
- Robot has two wheel encoders. In practice they don't track each
  other reliably (large value difference between the two, one side
  much noisier than the other even after filtering).
- Decision: run on a single "primary" encoder rather than trying to
  reconcile both in firmware. The disabled side is left in code
  (commented attachInterrupt call) so it can be re-enabled for testing.

CURRENT STATE (as of this entry)
- Active encoder: RIGHT wheel (R_A_PLUS / R_A_MINUS, pins 16 / 17).
- Disabled encoder: LEFT wheel (L_A_PLUS / L_A_MINUS, pins 14 / 15).
  Its attachInterrupt() call is commented out in setup().
- To swap which physical wheel is primary: comment/uncomment the
  attachInterrupt() calls in setup(), AND swap which current*Pulse /
  current*Glitch variable feeds encoder_data[0]/[2] in timer_callback()
  — the code always publishes the ACTIVE encoder at index [0]/[2],
  regardless of which physical wheel that is.

-----------------------------------------------------
CURRENT /wheel_encoder MESSAGE FORMAT (std_msgs/Int32MultiArray)
-----------------------------------------------------
encoder_data[0] = primary encoder pulse count   (currently: right wheel)
encoder_data[1] = secondary encoder pulse count (currently: left wheel, disabled — always 0)
encoder_data[2] = primary encoder glitch count   (rejected pulses: too narrow / too close together / arrived while stationary)
encoder_data[3] = secondary encoder glitch count (always 0 while that encoder is disabled)

Note: originally this was a Float32MultiArray. Switched to
Int32MultiArray because pulse/glitch counts are exact integers and
the robot is expected to run into the tens of thousands of wheel
revolutions — float32 only represents integers exactly up to 2^24
(~16.7M), beyond which consecutive counts start aliasing. int32 is
exact up to ~2.1 billion, effectively no ceiling for this use case.
If you ever see this on the Python side, it must subscribe as
Int32MultiArray, not Float32MultiArray.

-----------------------------------------------------
[2026-08-06] Feature: /reset_encoder topic (no more USB unplug to zero counters)
-----------------------------------------------------

PROBLEM
- Only way to zero the encoder pulse/glitch counters was to unplug and
  replug the USB cable between Teensy and Pi5 (forces a full reset —
  drops the whole micro-ROS session, not just the encoders).

FIX APPLIED
- Added a new subscription in src/main.cpp: /reset_encoder
  (std_msgs/msg/Empty). Any message received zeroes leftPulseCount,
  rightPulseCount, leftGlitchCount, rightGlitchCount under
  noInterrupts()/interrupts().
- rclc_executor_init() handle count bumped 2 -> 3 to fit the new
  subscription alongside cmd_vel and the timer.

USAGE (from the Pi)
    ros2 topic pub --once /reset_encoder std_msgs/msg/Empty {}

SECTION: micro-ROS / agent connection
=====================================================

1. IMU timestamp was never synced to real time
   - rmw_uros_epoch_millis() was being used for msg_imu.header.stamp,
     but rmw_uros_sync_session() was never called, so the epoch clock
     was never set from the agent — timestamps were meaningless (0 or
     time-since-boot).
   - Fix: added RCCHECK(rmw_uros_sync_session(1000)); in setup(),
     placed AFTER rclc_support_init() (that call is what actually
     creates the session — calling sync before it exists made setup()
     fail and drop the Teensy into the error-loop LED blink forever,
     which looked like "the agent can't connect").

2. Removed unused MAX_SPEED constant (dead code, only referenced in
   comments, not in any actual calculation).

-----------------------------------------------------
HOW TO DEBUG FURTHER / WHAT TO WATCH
-----------------------------------------------------
- `ros2 topic echo /wheel_encoder` while:
  a) robot sits still           -> [0]/[1] should not change; [2]/[3] may
                                    tick up if there's noise, that's fine.
  b) driving straight            -> [0] should increase/decrease smoothly
                                    with real motion.
  c) motor start (stop->move)    -> brief burst in [2] is expected
                                    (blanking window, first ~15ms), not
                                    a bug.
- If glitch counts stay unexpectedly high during normal driving,
  candidates to retune (src/main.cpp, near top "Encoder Noise Filtering"
  section):
    LEFT/RIGHT_ENCODER_DEBOUNCE_US   (gap between accepted pulses)
    LEFT/RIGHT_MIN_PULSE_WIDTH_US    (minimum valid pulse width)
    MOTOR_START_BLANK_MS             (length of stricter motor-start window)
    BLANK_MIN_PULSE_WIDTH_US / BLANK_ENCODER_DEBOUNCE_US (stricter values
                                       used only during that window)
- Real hardware fix (not yet done, still just a note in code comments):
  route encoder wires away from motor power leads, twisted pair /
  shielded cable, common ground, small decoupling cap (~0.1uF) across
  motor terminals — software filtering reduces symptoms but can't fully
  fix a badly-coupled signal.

SECTION: Distance calibration (pulses -> real-world distance)
=====================================================

-----------------------------------------------------
[2026-08-06] Raw calibration run data — heading_hold.py TARGET_PULSES stop test
-----------------------------------------------------

METHOD
- heading_hold.py drives straight and auto-stops once
  abs(pulses_traveled) >= abs(TARGET_PULSES) (see control_loop()).
- For each run: TARGET_PULSES set, script run once, actual pulse count
  at stop (raw, signed — this robot's encoder counts DOWN while
  driving forward) and the real-world distance (measured by hand, cm)
  were recorded.
- Firmware constants at time of this data: WHEEL_DIAMETER_MM=125,
  PULSES_PER_REV=1000, DISTANCE_SCALE_FACTOR=1.05 (see heading_hold.py).
  These are what the "round"(pulses)/cm numbers below should be used
  to re-derive, NOT numbers that were already applied to this data —
  the table below is raw sensor pulses vs. raw measured distance.

RAW DATA
  TARGET_PULSES = -35000 (11 runs):
    round(pulses)   cm
    -35082          194
    -35115          194
    -35040          190
    -35226          193
    -35197          190
    -35172          191
    -35173          191
    -35133          191
    -35250          192
    -35095          190
    -35167          190

  TARGET_PULSES = -70000 (5 runs):
    round(pulses)   cm
    -70155          385
    -70187          382
    -70183          383
    -70126          380
    -70105          382

QUICK STATS (computed from the raw data above)
  -35000 group:  avg |pulses| = 35150.9   avg cm = 191.45  ->  ~183.6 pulses/cm
  -70000 group:  avg |pulses| = 70151.2   avg cm = 382.4   ->  ~183.5 pulses/cm
  Both groups agree closely (~183.5 pulses/cm, i.e. ~18,350 pulses/meter),
  which is a good sign — the relationship looks linear and repeatable
  across the two distances tested.

  For comparison, the CURRENT firmware/script constants
  (WHEEL_DIAMETER_MM=125, PULSES_PER_REV=1000) imply only
  ~25.46 pulses/cm — about 7.2x lower than what was actually measured.
  This means the current METERS_PER_PULSE in heading_hold.py is far
  off; DISTANCE_SCALE_FACTOR=1.05 (a ~5% correction) is nowhere near
  enough to account for a ~7.2x gap. Likely explanation: PULSES_PER_REV
  and/or WHEEL_DIAMETER_MM in heading_hold.py don't match this
  encoder's real pulses-per-revolution or wheel size.

NEXT STEP (not yet applied — for whenever ready to recalibrate)
  Update heading_hold.py's WHEEL_DIAMETER_MM / PULSES_PER_REV (or just
  DISTANCE_SCALE_FACTOR directly) so that METERS_PER_PULSE reflects
  ~183.5 pulses/cm (~1.835 pulses/mm, ~18,350 pulses/m) instead of the
  current ~25.46 pulses/cm assumption.

-----------------------------------------------------
[2026-08-08] PULSES_PER_CM (112) is only valid at FORWARD_SPEED=0.20 / ROTATE_SPEED=0.20
-----------------------------------------------------

FINDING
- The current calibrated PULSES_PER_CM = 112 in grid_nav.py was derived
  from runs at FORWARD_SPEED = 0.20 and ROTATE_SPEED = 0.20 (raw PWM
  duty-cycle fractions, not real calibrated m/s or rad/s).
- Changing either speed changes real-world wheel speed, which changes
  the pulses-per-cm relationship (pulse width/gap relative to the
  encoder noise filters, wheel slip, etc.). Confirmed by testing:
  raising FORWARD_SPEED to 0.25 broke distance tracking badly enough
  that the robot appeared to "never stop."
- grid_nav.py's speed is now live-adjustable from the web GUI (Set
  Speed form) specifically to explore this relationship, but any run
  NOT at 0.20/0.20 should be treated as using an uncalibrated
  PULSES_PER_CM until re-derived for that speed.

RULE OF THUMB GOING FORWARD
  Only FORWARD_SPEED = 0.20 and ROTATE_SPEED = 0.20 are currently
  calibrated (PULSES_PER_CM = 112). If you run at any other speed,
  treat distance readings as unreliable and re-run the step-mode
  calibration procedure (drive box-by-box, measure with a ruler,
  recompute pulses/cm) for that specific speed before trusting it.

FUTURE IMPROVEMENT IDEA (not yet implemented)
  A real pulses/cm ratio is a fixed mechanical property (encoder
  pulses per wheel revolution, wheel circumference) -- it should NOT
  change with speed. The fact that it does points to pulses actually
  being dropped by the current software filtering in
  leftEncoderISR()/rightEncoderISR() (src/main.cpp): at higher wheel
  speed, real pulse widths/gaps shrink and start falling below
  LEFT/RIGHT_MIN_PULSE_WIDTH_US (60us) and/or
  LEFT/RIGHT_ENCODER_DEBOUNCE_US (200us), so they get miscounted as
  noise instead of real motion -- undercounting distance, which is
  consistent with the FORWARD_SPEED=0.25 "never stops" bug (target
  distance in pulses is never reached because pulses aren't arriving
  fast enough on the software side).

  Two possible fixes, not yet applied:
  1. BEST: switch to Teensy 4.1's dedicated hardware quadrature
     decoder peripheral (e.g. via the PJRC `Encoder` library, or
     QuadTimer/FlexPWM directly) instead of interrupt+debounce
     heuristics. Hardware counts edges directly and doesn't drop
     pulses at speed -- removes the need to ever recalibrate
     PULSES_PER_CM per speed again. Requires reworking how
     leftPulseCount/rightPulseCount are read (no more manual ISR
     width/gap filtering) and possibly re-checking pin assignments
     against what the hardware counter peripheral supports.
  2. QUICK/CHEAPER: loosen LEFT/RIGHT_MIN_PULSE_WIDTH_US and
     LEFT/RIGHT_ENCODER_DEBOUNCE_US so real pulses at higher speed
     (0.25+) stop being rejected. Faster to try, but is a guess-and-
     recheck loop and doesn't prevent the same problem recurring at
     an even higher speed later.

  Diagnostic step to confirm which pulses are being lost before
  picking a fix: compare wheel_encoder data[2] (glitch count) growth
  rate at 0.20 vs 0.25+ speed via `ros2 topic echo /wheel_encoder` --
  if glitch count climbs much faster relative to pulse count at the
  higher speed, that confirms the filter-clipping theory above.

SECTION: Camera HUD / distance rangefinder (grid_nav.py)
=====================================================

-----------------------------------------------------
[2026-08-08] Feature: USB webcam stream + backup-camera-style distance HUD
-----------------------------------------------------

WHAT WAS ADDED
- USB webcam streamed into the grid_nav.py GUI via OpenCV
  (CameraStreamer class) as MJPEG over a new /video_feed route.
  Requires `python3-opencv` (apt) or `opencv-python` (pip) on the Pi.
  CAMERA_DEVICE_INDEX picks which /dev/videoN to open (0 by default).
- CameraRangefinder class: turns the camera into a rough floor
  rangefinder using a small "+" crosshair fixed at the exact center
  of the video frame (the camera's optical axis).

HOW CALIBRATION WORKS (single-point, no lens data needed for this part)
- You physically point the robot/camera so the on-screen crosshair
  lines up with a floor mark at a KNOWN real-world distance, enter
  that distance + the camera's mounted height above the floor, and
  hit Calibrate.
- Because the crosshair point sits exactly on the optical axis, the
  camera-height/floor-distance/line-of-sight forms a simple right
  triangle -- no FOV or lens data needed to solve it:
      tilt_deg = atan(height_cm / known_distance_cm)
  tilt_deg is measured FROM HORIZONTAL (i.e. how far below level the
  camera's line of sight is) -- 0 deg = camera aimed dead level at
  the horizon, 90 deg = camera aimed straight down at its own feet.
  (If you want the angle from the vertical mounting pole instead,
  that's just 90 - tilt_deg.)
- Real numbers from this robot: height=26cm, calibrated at 100cm ->
  tilt_deg ~= 14.6 deg. That's a shallow, mostly-forward-looking
  angle, consistent with a low-mounted camera aimed at a fairly
  distant floor point.
- CALIBRATION DISTANCE CHOICE: originally tried calibrating at
  200cm, but that put the target mark too near the top of frame /
  vanishing point where a small pixel-alignment error maps to a
  large angular error -- switched to 100cm (closer, easier to align
  precisely, and roughly centered in the frame) for a more accurate
  tilt_deg. General rule: pick a calibration mark you can position
  precisely and that lands somewhere in the middle of the frame, not
  right at the blurry/compressed far edge.

FULL-FRAME PERSPECTIVE (the backup-camera-style guide lines)
- The single-point calibration above is enough to get tilt_deg (and
  therefore "distance at the crosshair"), but mapping ANY OTHER row
  of the image to a real-world distance additionally needs the
  camera's vertical field of view (vfov_deg), to get a pixel focal
  length:
      f_px = (frame_height_px / 2) / tan(vfov_deg / 2)
  then for a target real-world distance d:
      phi(d) = atan(height_cm / d)             -- required look-down angle
      y = frame_height_px/2 + f_px * tan(phi(d) - tilt_deg)
- vfov_deg is NOT solved from calibration -- it's a GUI-editable
  guess (default 45 deg, "typical-ish" for a USB webcam) since exact
  values aren't usually on the spec sheet. If the near guide line
  (e.g. the one at your calibration distance) looks right but
  farther lines (150cm+) don't match a tape measure, that's the
  value to nudge up/down and recalibrate against.
- GUIDE_DISTANCES_CM = [50, 100, 150, 200, 250, 300] draws horizontal
  lines at those real-world distances, color-coded red (<=100cm) /
  yellow (100-200cm) / green (>200cm), like a car's parking-assist
  camera -- lines naturally compress together near the horizon as
  distance increases, matching real floor perspective. Lines that
  would fall outside the visible frame for the current calibration
  are just skipped (not drawn).

NOT YET DONE / CAVEATS
- vfov_deg is a guess, not measured -- for real accuracy on the
  150cm+ lines, would need a second calibration point at a different
  known distance (two-point calibration solving both tilt_deg and
  vfov_deg together) instead of a fixed default.
- This whole feature assumes a perfectly flat, level floor and a
  rigidly fixed camera mount (no vibration/drift changing the tilt
  over time).
